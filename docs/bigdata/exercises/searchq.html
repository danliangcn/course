课程作业一：公共管理数据探索、清理与可视化

从数据可行性检查到可复现的视觉证据

发布于

2026年11月2日

作业的中心任务

围绕一个具体的公共管理问题，完成“实际获取数据—判断数据是否可用—审计数据质量—用代码完成清理—验证清理结果—制作可解释图表”的完整流程。

本作业不是比较谁使用的清洗函数更多，而是评价每一步是否有数据依据、能否重复运行，以及图表能否支持公共管理判断。

1 一、作业目标

完成本作业后，学生应能：

  1. 将公共管理问题转化为可由数据支持的分析问题；
  2. 判断数据来源、分析单位、时间范围和变量是否适合研究问题；
  3. 使用R完成数据导入、质量审计、清理、重组和验证；
  4. 区分缺失值、异常值、真实极端案例和录入错误；
  5. 使用程序化检查保证主键、连接和逻辑规则正确；
  6. 制作2—3张能够回答问题的图表，并解释证据边界；
  7. 判断该数据是否适合继续用于后续机器学习作业。

建议课外投入约 4—6小时。提交时间和具体平台以课程通知为准。

2 二、作业结构与进度

本作业分为两个阶段，但最终只计算一次正式作业成绩。

阶段 时间建议 主要任务 反馈方式
数据可行性检查 发布后3—4天内 提交问题、数据样例和数据检查卡 通过／修改后通过／更换数据
完整数据项目 发布后约两周 完成审计、清理、验证和可视化 按评分表计分
为什么必须先检查数据源？

仅仅找到一个网页或数据库名称，不等于已经获得可分析的数据。未通过可行性检查前，不建议投入大量时间写作或清洗。若首选数据无法下载、授权不清、变量不足或存在隐私风险，应尽早改用备用数据。

3 三、数据选择方式

数据可以来自：

  • 政府开放数据平台；
  • 统计年鉴或公开调查；
  • 环境、交通、健康、教育或公共服务监测；
  • 公开政策文本、政府工作报告或行政公报；
  • 合法、适度获取的网页公开信息；
  • 课程论文准备使用的其他公开数据。

自选数据必须满足：

  1. 已经实际获得，而不是只提供一个平台网址；
  2. 能够说明一行数据代表什么；
  3. 至少包含若干与问题相关的变量；
  4. 不包含未经授权的个人敏感信息；
  5. 可以在合理时间内完成导入和清理；
  6. 数据来源、获取日期和使用限制能够说明。

4 四、第一阶段：数据可行性检查

第一阶段不需要写长报告。提交一份1—2页的检查表和实际数据证据。

4.1 4.1 研究问题

提出：

  • 一个首选问题；
  • 一个备用问题；
  • 1—2篇与问题、数据或方法直接相关的文献。

推荐使用以下句式：

利用________数据，描述／比较／预测________公共管理现象，并分析其在________地区、时期或群体中的差异。

问题必须明确属于：

  • 描述：发生了什么、分布如何；
  • 预测：谁或何时更可能出现某种结果；
  • 因果：某项政策是否改变了结果。

本作业主要完成描述和探索。可视化中发现关联，不能直接写成政策因果效应。

4.2 4.2 数据可行性卡

检查内容 学生填写
数据名称与来源 机构、平台、网址或文献
获取日期与方式 下载、API、网页、申请或教师提供
分析单位 一行代表个人、地区、日期、工单、企业还是政策文本
时间范围 数据覆盖的起止时间
空间范围 全国、省、市、区县或具体机构
数据规模 行数、列数、文件格式和大致大小
主键 是否存在唯一标识；若无，可能由哪些字段组成
核心变量 与研究问题直接相关的变量
初步质量问题 缺失、重复、类型、异常编码或多表连接问题
获取与使用限制 是否需要申请、引用、匿名化或禁止再分发
备用方案 数据不可用时改用什么数据或调整什么问题

4.3 4.3 必须提供的实际证据

至少提供以下一项：

  • 原始数据前50—100行；
  • 可以重复运行的数据下载或导入代码；
  • 因授权不能提交原始数据时，提供脱敏样例、数据字典和获取说明。

同时提供：

glimpse(raw_data)
dim(raw_data)
head(raw_data)

只有网页介绍、截图或平台名称，不能视为已经获得数据。

5 五、第二阶段：完整数据项目

5.1 5.1 问题、文献与数据说明

用约500字说明：

  1. 核心公共管理问题；
  2. 问题为什么有公共价值；
  3. 相关文献怎样使用类似数据或方法；
  4. 数据的分析单位、时间和空间范围；
  5. 数据为什么能够支持该问题；
  6. 数据不能回答什么。

5.2 5.2 清理前数据审计

至少检查：

  • 行数和变量数；
  • 主键是否唯一；
  • 变量类型；
  • 各变量缺失数量和比例；
  • 完全重复记录；
  • 日期范围；
  • 分类变量的异常取值；
  • 数值变量的逻辑范围；
  • 多表连接时的键值唯一性和未匹配记录。

参考代码：

# 数据结构
glimpse(raw_data)
dim(raw_data)

# 主键重复数
sum(duplicated(raw_data$case_id))

# 批量统计缺失值
raw_data |>
  summarise(across(everything(), ~ sum(is.na(.x))))

# 查看分类变量的异常编码
raw_data |>
  count(district, sort = TRUE)

如果需要连接两张表，必须在连接前后检查：

# 检查左表键值是否唯一
left_table |>
  count(district) |>
  filter(n > 1)

# 找出无法匹配的键
left_table |>
  distinct(district) |>
  anti_join(right_table, by = "district")

5.3 5.3 有理由的数据清理

至少完成3项确有必要的清理，例如：

  • 变量类型和日期转换；
  • 主键去重；
  • 分类变量编码标准化；
  • 缺失值识别、标记、删除或插补；
  • 异常值识别和处理；
  • 正则表达式与 case_when() 合并文本类别；
  • 多表连接及匹配核查；
  • 长表与宽表转换；
  • 构造人均、比例、时长或其他公共管理指标。

每一步都必须说明：

发现了什么问题？为什么采用该规则？处理后怎样验证？

不要求每个数据集机械地完成所有清理操作。没有必要的Winsorize、插值、表格连接或长宽转换，不应为了凑数量而使用。

5.4 5.4 程序化质量验证

至少使用一次 stopifnot() 验证核心规则：

stopifnot(
  !anyDuplicated(clean_data$case_id),
  all(is.na(clean_data$response_hours) |
        clean_data$response_hours >= 0)
)

涉及多表连接时，还应验证不存在无法解释的未匹配键。验证失败时，不应直接删除报错代码，而应检查数据或修正规则。

5.5 5.5 清理前后比较

报告下列指标中适用于本数据的项目：

指标 清理前 清理后 变化原因
记录数
变量数
重复主键数
缺失单元格数
逻辑异常数
无法匹配记录数

记录数减少不自动代表清理正确。需要说明删除了哪些记录、依据是什么，以及是否可能造成选择偏差。

5.6 5.6 可视化证据

制作2—3张图：

  1. 一张展示数据分布或数据质量；
  2. 一张直接回答核心公共管理问题；
  3. 一张可选的时间、地区、群体或多变量比较图。

每张图必须包括：

  • 清楚的标题；
  • 坐标名称、单位和必要的数据来源；
  • 2—3句结果解释；
  • 对公共管理问题的含义；
  • 不能由该图推出的结论。

评分不以图表种类数量为依据。应根据变量和问题选择合适的图形，避免不必要的饼图、双坐标轴、三维效果和截断尺度。

5.7 5.7 是否适合后续机器学习？

在报告最后回答：

  1. 是否存在明确的目标变量？
  2. 目标变量是连续值还是类别？
  3. 是否有足够样本和可用特征？
  4. 哪些变量在真实预测时点能够获得？
  5. 是否存在由结果直接生成的泄漏变量？
  6. 应采用随机划分、时间划分还是分组划分？

如果数据更适合文本、空间、描述或因果分析，可以明确说明“不适合直接用于监督学习”。这不会降低本作业成绩，后续机器学习作业可以改用教师数据。

6 六、提交内容与目录结构

统一提交一个可以复现的项目文件夹：

assignment01/
├── assignment01.qmd
├── assignment01.html
├── README.md
├── data/
│   ├── raw/
│   └── clean/
└── figures/

要求：

  • raw/保存原始数据，不得手工覆盖；
  • clean/保存由代码生成的干净数据；
  • QMD能够从头运行并生成主要表格和图形；
  • 数据过大或禁止再分发时，提交下载代码、脱敏样例和说明；
  • 不再分别提交内容相互重复的R脚本、Word和PDF；
  • 文件名和相对路径中避免使用个人电脑的绝对路径。

7 七、评分标准

评分内容 比例
数据确实可得，研究问题与数据匹配 20%
清理前数据审计 15%
清理规则合理且解释清楚 25%
程序化质量验证 15%
可视化和公共管理解释 20%
可复现性、代码注释和AI使用说明 5%

评分重点是判断和验证，不按清洗函数、模型或图表的数量机械加分。

8 八、AI辅助使用规则

允许使用生成式AI：

  • 解释错误信息；
  • 建议清理代码；
  • 帮助理解函数参数；
  • 检查图表标注；
  • 改进代码注释和文字表达。

但必须满足：

  1. 不向AI上传含个人身份或敏感行政信息的数据；
  2. AI生成代码必须由本人运行和验证；
  3. 能够解释关键代码改变了什么数据；
  4. 在报告末尾简述AI用于哪些环节；
  5. 不得只提交AI生成的代码或解释文字；
  6. 教师可以抽取一段代码进行简短说明或课堂核验。
