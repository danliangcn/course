数据获取与预处理

从原始记录到可信的公共管理证据

发布于

2026年9月28日

本讲要解决的问题

公共管理数据很少是“下载后直接分析”的整洁表格。字段的形成往往受到行政流程、业务系统和填报行为的共同影响。因此，本讲不追求罗列所有文件格式，而是完成一条可重复的分析链：

明确问题 → 获取数据 → 审核质量 → 清理转换 → 合并验证 → 保存记录

本讲使用某市 12345 政务热线模拟数据。它不对应任何真实城市或个人，专门加入了常见的脏数据问题，便于课堂练习。

0.0.1 学习目标

完成本讲后，你应该能够：

  1. 根据研究问题判断需要什么数据，并记录数据来源与口径；
  2. 导入 CSV、Excel 和统计软件数据，先审核再清理；
  3. 处理不规范变量名、类型错误、特殊缺失值、重复记录和类别不一致；
  4. 使用键值连接两张表，并检查连接结果；
  5. 用程序化规则验证数据，输出可复现的清理结果；
  6. 解释数据质量问题背后的制度含义，而不只是“把 NA 删除”。
课堂原则

每完成一个步骤，都回答两个问题：

  • 这段代码改变了什么？
  • 这种改变会怎样影响公共管理结论？

1 进入课堂：先激活已有知识

1.1 3 分钟检索练习

不运行代码，先独立写出答案。

  1. filter()、select()、mutate() 分别改变数据的什么部分？
  2. NA 与字符串 "未评价" 有什么区别？
  3. 为什么课程项目应使用相对路径，而不是 setwd()？
  4. 如果同一个区县有两种写法，分组汇总会出现什么结果？
参考答案
  1. filter() 选择行，select() 选择列，mutate() 新建或修改列。
  2. NA 是 R 能识别的缺失值；"未评价" 是普通文本，必须先判断其业务含义再转换。
  3. 相对路径能让项目在不同电脑上保持可运行。
  4. R 会把它们视为不同类别，导致区县数量和汇总结果错误。

2 数据不是“自然产生”的

2.1 从研究问题倒推数据

假设研究问题是：

哪些类型、哪些区县的热线诉求回应较慢？回应速度与市民满意度之间有什么关系？

至少需要以下信息：

分析概念 可能的业务字段 需要核查的问题
诉求发生 提交时间、渠道 提交时间还是受理时间？
地理位置 区县、街道 按居住地还是事发地记录？
问题类型 事项类型 分类规则是否曾经调整？
政府回应 首次回应、办结时间 自动回复算不算回应？
处理结果 办结状态 “办结”是否等于问题解决？
公众评价 满意度 谁会评价？未评价意味着什么？

数据清理不是纯技术步骤。字段口径决定了我们最终能够提出多强的结论。

2.2 数据来源选择

公共管理研究常见的数据来源包括：

来源 优势 主要风险 课堂建议
政府开放数据 权威、连续 口径变化、更新滞后 先读元数据
行政业务记录 细粒度、过程性强 制度性筛选、隐私风险 明确生成流程
调查数据 可测量态度和感知 抽样与回应偏差 检查问卷和权重
网页与平台数据 更新快、内容丰富 合规性、代表性、页面变化 保存来源与抓取日期
API / 数据库 自动化、可扩展 权限、配额、查询错误 先小规模测试
数据来源记录卡

每组选择一个课程项目候选数据源，记录：数据提供者、链接或文件位置、覆盖时间、分析单位、关键变量、更新频率、许可与隐私限制，以及它能回答和不能回答的问题。

3 获取并导入数据

3.1 建立可复现的项目目录

建议一个研究问题对应一个 RStudio Project：

hotline-project/
├── data/
│   ├── raw/          # 原始文件，只读保存
│   └── processed/    # 清理后的数据
├── R/                # 清理与分析脚本
├── figures/
├── output/
├── report.qmd
└── hotline-project.Rproj

不要修改 data/raw/ 中的原始文件。所有修改都写入脚本，并把结果另存到 data/processed/。

3.2 常见文件格式

# CSV / TSV
hotline <- readr::read_csv("data/raw/hotline.csv")
hotline <- readr::read_tsv("data/raw/hotline.tsv")

# Excel：需要 readxl 包
hotline <- readxl::read_excel(
  "data/raw/hotline.xlsx",
  sheet = "案件明细"
)

# Stata / SPSS / SAS：需要 haven 包
survey <- haven::read_dta("data/raw/survey.dta")
survey <- haven::read_sav("data/raw/survey.sav")
survey <- haven::read_sas("data/raw/survey.sas7bdat")

导入真实文件时，先保留原始列为字符型，完成审计后再转换，能够避免日期或编号被软件自动误判。

4 先审计，再清理

4.1 第一眼检查

dim(hotline_raw)
[1] 25  9
names(hotline_raw)
[1] "案件编号" "提交时间" "区县"     "事项类型" "首次回应" "办结状态" "办结时间"

# 每列可见的不同取值数量
hotline_raw |>
# 对所有的变量统计不同的值的个数，并总结成一行
  summarise(across(everything(), n_distinct)) |>
# 整理结果，从宽格式转换为长格式
  pivot_longer(everything(), names_to = "variable", values_to = "n_unique")

不要一打开数据就连续写 mutate()。先检查：

  • 行和列是否符合预期；
  • 编号能否唯一识别案件；
  • 日期和数值是否被读成正确类型；
  • 类别是否有空格、错别字或不同口径；
  • 缺失值用了哪些符号；
  • 是否存在重复记录和逻辑矛盾。

4.2 12 分钟脏数据诊断

四人一组，不修改数据，只完成“问题—证据—风险”表。

发现的问题 用什么证据确认 不处理会造成什么后果
例如：区县写法不一致 count(区县) 同一区县被拆成多组

下面的代码能帮助诊断。

hotline_raw |> count(区县, sort = TRUE)
hotline_raw |> count(事项类型, sort = TRUE)
hotline_raw |> count(满意度, sort = TRUE)
# 检查重复编号
hotline_raw |>
  count(案件编号, name = "n") |>
  filter(n > 1)
至少应该发现的六类问题
  1. 日期格式不一致；
  2. 区县名称有空格或省略“区”；
  3. 事项类型存在空格和近义类别；
  4. 首次回应同时使用“小时”“天”和文本编码；
  5. 满意度用 -99、-、未评价 表示缺失；
  6. C006 重复，且 C015 的办结时间早于提交时间。

4.3 生成可复查的数据质量摘要

special_missing <- c("", "-", "-99", "未评价", "未回应")

5 清理字段：名称、类型与取值

5.1 第一步：把变量名改成稳定的英文名称

hotline_step1 <- hotline_raw |>
  rename(
    case_id = 案件编号,
    submitted_raw = 提交时间,
    district_raw = 区县,
    issue_raw = 事项类型,
    response_raw = 首次回应,
    status_raw = 办结状态,
    closed_raw = 办结时间,
    satisfaction_raw = 满意度,
    channel = 渠道
  ) |>
# 找到所有的字符型变量，每列执行空格清理工作
  mutate(across(where(is.character), str_squish))

names(hotline_step1)

[5] "response_raw"     "status_raw"       "closed_raw"       "satisfaction_raw"

英文变量名便于写代码；中文变量标签可以在表格和图形阶段再添加。str_squish() 会去掉首尾空格，并把连续空格压缩为一个。

5.2 第二步：识别特殊缺失值

hotline_step2 <- hotline_step1 |>
  mutate(
    response_raw = replace(
      response_raw,
      response_raw %in% c("", "-", "未回应"),
      NA_character_
    ),
    closed_raw = replace(
      closed_raw,
      closed_raw %in% c("", "-"),
      NA_character_
    ),
    satisfaction_raw = replace(
      satisfaction_raw,
      satisfaction_raw %in% c("", "-", "-99", "未评价"),
      NA_character_
    )
  )

hotline_step2 |> count(satisfaction_raw, sort = TRUE)
不要把所有特殊编码机械地转成 NA

先读数据字典。某些系统中 -99 可能代表“不适用”，而不是“漏填”。不同原因的缺失值可能需要先保留为不同类别，再决定如何分析。

5.3 第三步：统一行政区与事项类别

hotline_step3 <- hotline_step2 |>
  mutate(
    district = case_when(
      district_raw %in% c("思明", "思明区") ~ "思明区",
      district_raw %in% c("湖里", "湖里区") ~ "湖里区",
      district_raw %in% c("集美", "集美区") ~ "集美区",
      district_raw %in% c("海沧", "海沧区") ~ "海沧区",
      district_raw %in% c("同安", "同安区") ~ "同安区",
      district_raw %in% c("翔安", "翔安区") ~ "翔安区",
# 如果都没有匹配则保留原值
      TRUE ~ district_raw
    ),
    issue_type = case_when(
      issue_raw %in% c("环境卫生", "环境 卫生", "市容环境") ~ "市容环境",
      issue_raw %in% c("交通", "交通出行") ~ "交通出行",
      issue_raw %in% c("公共服务", "公共 服务") ~ "公共服务",
      TRUE ~ issue_raw
    ),
    status = recode(
      status_raw,
      "办结" = "已办结",
      "未办结" = "处理中"
    )
  )

hotline_step3 |> count(district)
hotline_step3 |> count(issue_type)

实际项目不要凭感觉合并类别。应保存映射表，并让熟悉业务口径的人确认。

5.4 第四步：转换日期、时长和满意度

hotline_step4 <- hotline_step3 |>
  mutate(
    
    # 将 submitted_raw 从字符型文本解析为真正的日期时间变量
    submitted_at = parse_date_time(
      submitted_raw,
      
      # orders 指定可能出现的日期时间格式
      # "ymd HM"：年-月-日 时:分，例如 2026-09-28 14:30
      # "Ymd HM"：紧凑格式，例如 20260928 14:30
      # "dmy HM"：日-月-年 时:分，例如 28-09-2026 14:30
      orders = c("ymd HM", "Ymd HM", "dmy HM"),
      
      # 指定时区为中国标准时间
      tz = "Asia/Shanghai"
    ),
    
    
    # 将 closed_raw 同样解析为日期时间变量
    closed_at = parse_date_time(
      closed_raw,
      orders = c("ymd HM", "Ymd HM", "dmy HM"),
      tz = "Asia/Shanghai"
    ),
    
    
    # 将 response_raw 中不同单位的回应时长统一换算成“小时”
    response_hours = case_when(
      
      # 如果 response_raw 中包含“天”
      # parse_number() 提取其中的数字，再乘以24换算成小时
      # 例如 "2天" -> 2 * 24 = 48小时
      str_detect(response_raw, "天") ~
        parse_number(response_raw) * 24,
      
      # 如果包含“小时”，直接提取数字
      # 例如 "6小时" -> 6
      str_detect(response_raw, "小时") ~
        parse_number(response_raw),
      
      # 其他无法识别的情况设为数值型缺失值 NA
      TRUE ~ NA_real_
    ),
    
    
    # 将文字型满意度转成数值评分
    satisfaction_score = recode(
      satisfaction_raw,
      "不满意" = 1,
      "一般" = 2,
      "满意" = 3,
      "很满意" = 4,
      
      # 没有匹配上述四种情况的值，一律设为数值型 NA
      .default = NA_real_
    )
  )

invalid_records <- hotline_unique |>
  mutate(
    
    # 检查回应时间是否异常：
    # 小于0小时，或者大于30天（24*30=720小时），都标记为 TRUE
    invalid_response =
      response_hours < 0 |
      response_hours > 24 * 30,
    
    
    # 检查时间逻辑是否异常：
    # 只有 closed_at 不是缺失值时才检查；
    # 如果办结时间早于提交时间，则标记为 TRUE
    invalid_time =
      !is.na(closed_at) &
      closed_at < submitted_at,
    
    
    # 检查满意度分数是否异常：
    # 只有 satisfaction_score 不是 NA 时才检查；
    # 如果分数不在1到4之间，则标记为 TRUE
    invalid_score =
      !is.na(satisfaction_score) &
      !between(satisfaction_score, 1, 4)
  ) |>
  
  # 只要三个异常条件中任意一个为 TRUE，

    invalid_response |
    invalid_time |
    invalid_score

  select(
    case_id,
    submitted_at,
    closed_at,
    response_hours,

    starts_with("invalid_")

7.1 缺失模式

missing_summary <- hotline_clean |>
  
  # 对所有变量分别计算缺失比例
  # is.na(.x) 会得到 TRUE/FALSE
  # mean() 会把 TRUE 当作1、FALSE当作0
  # 所以平均值就是“缺失值占全部观测的比例”
  summarise(
    across(
      everything(),
      ~ mean(is.na(.x))
    )
  ) |>
  
  # 将“宽格式”转换成长格式
  # 原来的变量名放到 variable 列
  # 各变量对应的缺失率放到 missing_rate 列
  pivot_longer(
    everything(),
    names_to = "variable",
    values_to = "missing_rate"
  ) |>
  
  # 按 missing_rate 从高到低排序
  # desc() 表示 descending，即降序
  arrange(desc(missing_rate))

7.2 制度性缺失

满意度缺失可能是：

  • 案件尚未办结，所以暂时不能评价；
  • 市民没有主动评价；
  • 某些渠道不支持评价；
  • 系统迁移时字段丢失。

因此，“有满意度的案件”未必代表全部案件。只分析已评价案件，可能系统性排除处理较慢或使用特定渠道的人群。

hotline_clean |>
  
  # 新建 evaluated 变量：
  # satisfaction_score 不是 NA → TRUE，表示“已评价”
  # satisfaction_score 是 NA     → FALSE，表示“未评价”
  mutate(
    evaluated = !is.na(satisfaction_score)
  ) |>
  
  # 按 status 和 evaluated 两个变量组合计数
  # n 表示每种组合有多少条记录
  count(status, evaluated) |>
  
  # 按 status 分组
  # 后面的比例计算会在每一种 status 内部分别进行
  group_by(status) |>
  
  # 计算每个 status 内，“已评价/未评价”各自所占比例
  # n 是当前这一类的数量
  # sum(n) 是当前 status 下的总案件数
  mutate(
    rate = n / sum(n)
  ) |>
  
  # 取消分组，避免后续操作继续受到 status 分组影响
  ungroup()
本讲不要求插补

对这份行政过程数据，当前重点是描述缺失、解释缺失机制并做敏感性判断。均值插补或 KNN 插补不会自动消除偏差，且可能制造虚假的精确性。

13 本讲小结

可信的数据预处理流程应当做到：

  1. 保留原始数据：不覆盖、不手工悄悄修改；
  2. 先审计后清理：先理解问题，再写转换规则；
  3. 明确分析单位：知道一行、一列和主键代表什么；
  4. 解释缺失机制：把行政过程和选择偏差纳入判断；
  5. 连接前后检查键值：避免静默丢失和多对多扩张；
  6. 把规则写成测试：让错误尽早暴露；
  7. 记录所有决定：使他人能够复核和重现。

  summarise(n = n()) |>
  collect()

dbDisconnect(con)

collect() 之前的操作尽量在数据库端完成。始终使用只读权限，避免在分析脚本中修改生产数据库。

16 附录 C：Parquet、Arrow 与 DuckDB

Parquet 是列式存储格式，适合体量较大、重复读取的数据。

library(arrow)

hotline_ds <- open_dataset("data/raw/hotline_parquet/")

district_result <- hotline_ds |>
  filter(year(submitted_at) == 2025) |>
  group_by(district) |>
  summarise(n = n()) |>
  collect()

DuckDB 也可以直接查询 CSV 和 Parquet，适合在本地进行较大数据分析。不要因为课程名中有“大数据”就过早优化；先测量瓶颈，再选择工具。

17 附录 D：JSON、嵌套数据与 API

API 常返回 JSON。请求之前应阅读文档，确认认证方式、速率限制、字段含义和数据许可。

library(httr2)
library(jsonlite)

response <- request("https://api.example.gov/v1/cases") |>
  req_url_query(page = 1, page_size = 100) |>
  req_retry(max_tries = 3) |>
  req_perform()

payload <- resp_body_json(response, simplifyVector = TRUE)
cases <- as_tibble(payload$data)

嵌套列表可以使用 tidyr::unnest_longer()、unnest_wider() 或 hoist() 展开。保存原始响应、请求时间和参数，便于复核。

18 附录 E：网页抓取与合规边界

网页抓取应当是最后选择，而不是默认的数据获取方法。优先寻找开放数据下载、官方 API 或可授权的数据接口。

library(rvest)

# 推荐先把允许使用的页面保存为本地 HTML，再开发选择器
page <- read_html("data/raw/saved_page.html")

items <- page |>
  html_elements(".result-item") |>
  html_text2()

抓取前至少检查：

  • 网站服务条款和 robots.txt；
  • 是否包含个人信息或敏感信息；
  • 请求频率是否会影响服务；
  • 是否能保存抓取日期、页面版本和代码；
  • 数据是否具有足够代表性。

动态网页可能需要浏览器自动化，但技术上可抓取不代表伦理上或法律上可使用。
